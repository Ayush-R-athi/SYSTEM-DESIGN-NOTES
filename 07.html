The Problem — Distributing Data Across Servers

Imagine your app has grown massively. You have millions of users and a huge amount of data. A single database can't handle all of it anymore — it becomes a bottleneck.

The solution is Horizontal Scaling: add more database servers and split the data across them.

📦 Horizontal Scaling — Splitting Data
  Before (1 server):                After (3 servers):
  ┌──────────────────┐     ┌──────────┐ ┌──────────┐ ┌──────────┐
  │   DB (100% load) │  →  │  DB-0    │ │  DB-1    │ │  DB-2    │
  │  all data here   │     │ ~33% data│ │ ~33% data│ │ ~33% data│
  └──────────────────┘     └──────────┘ └──────────┘ └──────────┘

  Problem: How do we decide which data goes to which server?
  And more importantly — how do we FIND it again later?
The core challenge: You need a rule (an algorithm) that — given a piece of data — always tells you the same server to put it in AND the same server to look for it in. This rule must be consistent every time.
2

Hash Functions — The Naive Approach

The first idea: write a hash function that maps a user's ID to a server index.

Simple Hash Function
server_index = user_id MOD number_of_servers

Example with 3 Servers

🔢 Hash Function: user_id MOD 3
  Users:       Piyush (id=1)   John (id=2)   Jane (id=3)   Alex (id=4)   Tiger (id=5)

  Calculation:
    1 MOD 3 = 1  →  Piyush's data  → DB-1
    2 MOD 3 = 2  →  John's data    → DB-2
    3 MOD 3 = 0  →  Jane's data    → DB-0
    4 MOD 3 = 1  →  Alex's data    → DB-1
    5 MOD 3 = 2  →  Tiger's data   → DB-2

  ┌──────────┐   ┌──────────┐   ┌──────────┐
  │  DB-0    │   │  DB-1    │   │  DB-2    │
  │  Jane    │   │  Piyush  │   │  John    │
  │          │   │  Alex    │   │  Tiger   │
  └──────────┘   └──────────┘   └──────────┘
What makes a good hash function?
1. Deterministic — same input ALWAYS gives same output (never random)
2. One-way — you can't reverse it (index 1 → can't figure out it was Piyush)
3. Even distribution — data is spread roughly equally across servers
🎯
Why NOT use random? If you store Piyush in DB-2 and later look him up, random gives you DB-0. Data is lost! The function MUST be deterministic — same input, same output, every single time.

This simple approach works great... until you need to add or remove a server. That's when everything breaks.

3

The Big Problem — Adding or Removing a Server

Your platform keeps growing. You now need a 4th database server. Sounds simple — just add it, right? Wrong. Adding one server changes the hash function, which breaks ALL existing data lookups.

💥 What Happens When You Add a 4th Server
  OLD hash function: user_id MOD 3
  NEW hash function: user_id MOD 4  ← changed!

  Data is still in old positions. But lookups use new function:

  Jane  (id=3): OLD → 3 MOD 3 = 0 → was in DB-0 ✅
                NEW → 3 MOD 4 = 3 → looks in DB-3 ❌ NOT THERE!

  Alex  (id=4): OLD → 4 MOD 3 = 1 → was in DB-1 ✅
                NEW → 4 MOD 4 = 0 → looks in DB-0 ❌ NOT THERE!

  Tiger (id=5): OLD → 5 MOD 3 = 2 → was in DB-2 ✅
                NEW → 5 MOD 4 = 1 → looks in DB-1 ❌ NOT THERE!

  John  (id=2): OLD → 2 MOD 3 = 2 → was in DB-2 ✅
                NEW → 2 MOD 4 = 2 → looks in DB-2 ✅ (lucky!)

  Result: 3 out of 5 users can't find their data! 💥

❌ Simple Hashing (MOD n)

~75%

of all keys need to be moved when adding/removing a server

With 5 million records → move ~3.75 million records

System downtime, data inconsistency, massive I/O cost

✅ Consistent Hashing

~1/n

of keys need to move when adding/removing a server

With 5 million records → move only ~1.25 million records

Minimal disruption, no downtime, efficient

❌ The root problem with simple hashing: The formula user_id MOD n depends on n (number of servers). Change n, and the formula changes for ALL data. You have to reshuffle almost everything.
4

What is Consistent Hashing?

Consistent Hashing = A technique that maps both servers AND data onto a ring (circle). Data is assigned to the nearest server going clockwise. When a server is added or removed, only the data between that server and its predecessor needs to move — everything else stays.

❌ Simple Hashing

  • Formula: key MOD n
  • All data mapped to a server directly
  • Depends on n (number of servers)
  • Change n → remap almost everything
  • Massive data movement on scale up/down

✅ Consistent Hashing

  • Both servers AND data on a ring
  • Data goes to nearest server clockwise
  • Adding a server only affects nearby keys
  • Removing only affects that server's keys
  • Minimal data movement — only a fraction
Used by real systems: Amazon DynamoDB, Apache Cassandra, Discord's chat service, and many distributed databases use Consistent Hashing to distribute data across nodes efficiently.
5

The Hash Ring — How It Works

The core idea: imagine a clock. The hash function maps everything to a number between 1 and 12 (or in real systems, 0 to 2³² - 1). Arrange those numbers in a circle — that's the Hash Ring.

🔄 The Hash Ring — Placing 3 Servers

How the Ring is Built — Step by Step

1
Create the ring The hash function maps values to a range (e.g. 1–12, like a clock). Arrange these numbers in a circle.
2
Place servers on the ring Each server has an IP address or identifier. Feed it through the hash function. Place the server at the number it returns. Example: Server-0 → hash → 9, Server-1 → hash → 2, Server-2 → hash → 5.
3
Place data on the ring Each piece of data (e.g. user ID) also goes through the hash function. It lands somewhere on the ring too.
4
Find the server — go CLOCKWISE From where the data lands on the ring, move clockwise until you hit the first server. That's the server that stores this data.
6

Inserting Data Into the Ring

📥 How Data is Stored in Consistent Hashing
  Ring positions: 1–12 (like a clock)
  Servers:  S-0 at pos 9 | S-1 at pos 2 | S-2 at pos 5

  Data item 1 → hash → lands at position 1
    Go clockwise from 1... next server = S-1 (at 2)
    → Store in S-1 ✅

  Data item 2 → hash → lands at position 6
    Go clockwise from 6... next server = S-0 (at 9)
    → Store in S-0 ✅

  Data item 3 → hash → lands at position 3
    Go clockwise from 3... next server = S-2 (at 5)
    → Store in S-2 ✅

  Data item 4 → hash → lands at position 10
    Go clockwise from 10... past 11, 12, 1, 2... next server = S-1 (at 2)
    Wait — from 10 clockwise, we first hit S-1 at pos 2? No.
    From 10 clockwise: 11→12→1→2 = S-1
    → Store in S-1 ✅
The lookup rule (always same):
1. Hash the key → get a position on the ring
2. Go clockwise from that position
3. First server you hit → that's where the data lives

This same rule is used for both inserting and reading data. Guaranteed to always find the same server!
7

Adding a Server — Minimal Data Movement

Here's where Consistent Hashing shines. Let's add a new server S-3 which hashes to position 12.

➕ Adding Server S-3 at Position 12
  BEFORE (ring): S-1(2) → S-2(5) → S-0(9) → [back to S-1]

  New server S-3 added at position 12:
  AFTER  (ring): S-1(2) → S-2(5) → S-0(9) → S-3(12) → [back to S-1]

  Which data needs to move?
  ┌──────────────────────────────────────────────────────┐
  │ Only data that was between position 9 and 12!        │
  │ (that data used to go to S-1, now goes to S-3)       │
  │                                                       │
  │ Data at positions 1,2,3,4,5,6,7,8 → NOT affected ✅  │
  │ Data at positions 10,11,12 → move from S-1 → S-3 📦  │
  └──────────────────────────────────────────────────────┘

  In a system with 5 million keys:
  Simple hashing  → ~3.75 million keys need to move ❌
  Consistent hash → only ~417,000 keys move (≈1/12 of total) ✅
✅ Why only keys between prev server and new server move:
Those keys were previously "claimed" by the first server clockwise (which was S-1 past position 9). Now that S-3 is between them, those keys find S-3 first. All other keys still find the same server they did before — nothing else changes!
🏘️
Neighbourhood analogy: Imagine the ring is a road in a circle. Servers are post offices. Each house sends mail to the nearest post office clockwise. You open a NEW post office — only the houses between the old and new post office need to change where they send mail. All other houses are unaffected.
8

Removing a Server — Same Idea

➖ Removing Server S-2 (position 5)
  BEFORE: S-1(2) → S-2(5) → S-0(9) → S-3(12) → [back]

  S-2 crashes / is removed:
  AFTER:  S-1(2) → S-0(9) → S-3(12) → [back to S-1]

  Which data needs to move?
  ┌──────────────────────────────────────────────────────┐
  │ Only the data that WAS stored in S-2!                │
  │ (data at positions 3, 4, 5 — between S-1 and S-2)   │
  │ These now go clockwise to S-0 (next available)       │
  │                                                       │
  │ Data in S-0, S-1, S-3 → NOT affected ✅              │
  │ Data in S-2 → redistributed to S-0 (clockwise) 📦   │
  └──────────────────────────────────────────────────────┘
How to find affected keys when removing a server:
Go anti-clockwise from the removed server until you hit the previous server. All keys in that range need to be redistributed to the next server clockwise. Easy to calculate, minimal in scope.

The Hotspot Problem & Virtual Nodes

There's one remaining problem with basic Consistent Hashing. If the hash function places servers unevenly on the ring, one server ends up with a much larger slice of the ring — and therefore much more data.

⚠️ Uneven Server Placement = Hotspot
  Ring:
  S-0 at position 1
  S-1 at position 3   ← very close to S-0!
  S-2 at position 8

  Result:
  S-0 handles keys from 8 → 1  (small slice, ~25% of ring)
  S-1 handles keys from 1 → 3  (tiny slice, ~17% of ring)
  S-2 handles keys from 3 → 8  (HUGE slice, ~58% of ring) ← HOTSPOT!

  S-2 gets more than 2× the traffic of the others! 💥
⚠️ Hotspot problem: When servers cluster together on the ring, one server gets assigned a disproportionately large portion and becomes overloaded while others are idle.

Solution: Virtual Nodes

Virtual Nodes = Instead of placing each server at ONE point on the ring, place it at multiple points. Each "virtual node" is just a pointer to the real server. This distributes load far more evenly.
✅ Virtual Nodes — Even Load Distribution
  Without Virtual Nodes:
  Ring: ... S-2 ... S-2 gets huge chunk ...

  With Virtual Nodes (3 virtual nodes per server):
  S-0 real server at 1, virtual copies at 5, 9
  S-1 real server at 3, virtual copies at 7, 11
  S-2 real server at 8, virtual copies at 2, 12

  Ring: S-0(1) → S-1(3) → S-0v(5) → S-1v(7) → S-2(8) → S-0v(9) → S-1v(11) → S-2v(12) → ...

  Result: Every server handles multiple small slices
  → Load is distributed much more evenly across real servers ✅

❌ Without Virtual Nodes

  • Each server = 1 point on ring
  • Uneven hash can create huge slices
  • One server becomes overloaded (hotspot)
  • Others are underutilized — wasted resources

✅ With Virtual Nodes

  • Each server = multiple points on ring
  • Slices are smaller and more evenly spread
  • Even if one cluster has bad luck, others compensate
  • Standard practice in production systems
🏪
Virtual Nodes analogy: Imagine a city with 3 supermarkets. If all 3 are in one corner, all customers from the other side travel far. But if each supermarket opens 2 extra branches around the city, everyone has a nearby store. Virtual nodes are like those branches — same supermarket, just more locations.

Full Summary & Real-World Usage

The Full Journey — From Problem to Solution

1
Problem: Single DB is a bottleneck Too much data for one server → horizontal scaling → need to split data across multiple servers.
2
Naive fix: user_id MOD n Works until you add/remove a server. Changing n reshuffles almost ALL data — massive, disruptive data movement.
3
Better fix: Consistent Hashing with a Ring Map both servers and data onto a ring. Data finds its server by going clockwise. Only keys between two servers are affected when one is added/removed.
4
Refinement: Virtual Nodes Each server sits at multiple positions on the ring, ensuring even load distribution even when the hash function places real servers unevenly.

Key Concepts at a Glance

ConceptWhat it means
Hash FunctionTakes an input (user ID, server IP) and returns a deterministic, fixed-range number. Same input → always same output.
DeterministicSame input always produces the same output. Without this, you could never reliably find your data again.
Hash RingA circle of hash values (like a clock). Both servers and data are placed on this ring.
Clockwise lookupFrom data's ring position, go clockwise to find its server. Used for both reads and writes.
Minimal redistributionAdding/removing a server only moves keys in the affected arc — not the whole dataset.
Virtual NodesEach real server has multiple positions on the ring to ensure even load distribution.
HotspotWhen one server gets overloaded because it owns a disproportionately large arc of the ring.

Consistent Hashing vs Simple Hashing

❌ Simple Hashing (key MOD n)

  • Formula changes when n changes
  • Add 1 server → reshuffle ~75% of all data
  • Remove 1 server → same massive reshuffle
  • Works fine at fixed, small scale
  • Not suitable for dynamic scaling

✅ Consistent Hashing (ring)

  • Formula is independent of server count
  • Add 1 server → move only ~1/n keys
  • Remove 1 server → only that server's keys move
  • Scales dynamically with minimal disruption
  • Industry standard for distributed systems
