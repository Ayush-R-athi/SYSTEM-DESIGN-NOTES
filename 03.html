What is an Event?

In a big system like Amazon, users are constantly doing things — clicking, buying, updating. Each of these actions is called an Event.

Event = Any action a user performs on your platform that changes something.

Examples of Events on Amazon

🛒 Amazon Events
ADD_ITEM_TO_CART
User added a product to their cart
CHECKOUT_ITEM
User placed an order
PRODUCT_UPLOADED
A seller added a new product
PRODUCT_PRICE_UPDATED
A seller changed a product's price from ₹90 to ₹100
ORDER_CANCELLED
User cancelled their order

Every click, every update, every purchase — they're all events. Big systems process millions of these events every second.

2

Traditional CRUD Approach & Its Problems

The way most developers handle events is simple: when something happens, update the database directly. This is the CRUD (Create, Read, Update, Delete) approach.

📝 Traditional CRUD Flow
  User requests: "Change product price to ₹100"
         |
         ▼
  API Gateway → Nginx (Reverse Proxy) → Server
         |
         ▼
  Server runs SQL:
  UPDATE products SET price = 100 WHERE id = 1;
         |
         ▼
  Database row is updated (old value LOST forever)
         |
         ▼
  Next read: returns ₹100 ✅

Problems with CRUD at Scale

❌ Problem 1: Database Locking

  • To update a row, you must acquire a lock
  • While locked, no one can read that row
  • High-frequency updates → constant locking
  • Bottleneck for all readers
  • Race conditions possible

❌ Problem 2: State is Lost

  • You only store the CURRENT value
  • Old values are permanently overwritten
  • No way to know what happened before
  • Can't audit: "why is the price ₹100 now?"
  • Can't see history or replay events
⚠️ Race Condition Example:
Seller updates price to ₹100. At the exact same millisecond, a buyer reads the price. The buyer might see ₹90 (old value) because the lock hadn't been released yet. With many concurrent updates, this is a constant problem.
3

The State Management Problem — Video Pipeline

Let's understand the deeper problem with a real example: building a YouTube-like video processing pipeline.

When you upload a video to YouTube, it doesn't go live immediately. It gets processed — converted to 360p, 480p, 720p, 1080p, 4K, transcribed, optimized. This takes time (10–20 minutes even with good servers).

The Naive Design (CRUD approach)

🎬 Video Pipeline States (Traditional Way)
  Video uploaded by user
         │
         ▼
  DB: status = "UPLOADED"   ← update DB
         │
  Worker pool picks up video
         ▼
  DB: status = "PROCESSING" ← update DB
         │
  Worker done, re-uploads processed video
         ▼
  DB: status = "SUCCESS"    ← update DB
  (or "FAILED" if error)

What Goes Wrong?

❌ Failure Scenario 1: Upload success, but DB update fails
Video is uploaded to S3 successfully, but the DB update to "UPLOADED" fails (DB was busy). The status stays at whatever it was before. The video exists but is never picked up by workers. It's stuck forever!
❌ Failure Scenario 2: Processing happens, but status never updates
Worker picks up the video and starts processing it. But the DB update to "PROCESSING" fails. The status stays "UPLOADED". Another worker might pick it up again and process it twice!
❌ Failure Scenario 3: Success, but status stays "PROCESSING"
The video processes and re-uploads successfully. But the final DB update to "SUCCESS" fails. The status stays "PROCESSING" forever. User complains: "My video is stuck!"
The root cause: You're trying to keep two sources of truth in sync — what's actually happening in the system AND what the database says. These can go out of sync any time a DB write fails. And you have no way to trace back where exactly things went wrong.
4

What is Event Sourcing?

Event Sourcing says: instead of updating a database when something happens, just record that something happened. The events themselves ARE the source of truth.

Core idea: Never directly update state in a database. Instead, emit (record) an event every time anything happens. The current state can always be derived by replaying all events in order.

❌ Traditional CRUD

  • Store only the latest state
  • Update row in DB when something changes
  • Old state is lost forever
  • DB is the source of truth
  • State can go out of sync

✅ Event Sourcing

  • Store ALL events, never delete
  • Append new event when something happens
  • Full history is always available
  • Events are the source of truth
  • Current state is derived from events
📖
Analogy — Bank Ledger vs Bank Balance:
Traditional: Just store current balance (₹500). History is gone.
Event Sourcing: Keep a full ledger — every deposit, every withdrawal. Balance is always calculated from ledger entries. Banks work exactly this way!
5

Event Log — The Append-Only Log

In Event Sourcing, all events are stored in an Event Log — a special kind of storage that only allows adding new entries. You can never modify or delete past entries.

Append-Only Log = You can only ADD to the end. Never edit. Never delete.
Why? Because events happened in the past. You can't change what happened. A video was uploaded before it was processed — that order can never reverse.
📜 Event Log for Video Pipeline (Append-Only)
VIDEO_UPLOADED
videoId: "abc123", path: "s3://bucket/abc123.mp4" | 10:00:00 AM
VIDEO_PROCESSING_STARTED
videoId: "abc123", workerId: "worker-2" | 10:05:00 AM
VIDEO_PROCESSING_PROGRESS
videoId: "abc123", progress: "30%" | 10:08:00 AM
VIDEO_PROCESSING_PROGRESS
videoId: "abc123", progress: "70%" | 10:10:00 AM
VIDEO_PROCESSING_SUCCESS
videoId: "abc123", outputPath: "s3://bucket/processed/abc123/" | 10:12:00 AM

Each event has: an event name, data (relevant info), and a timestamp. Events are stored in order they happened, forever.

Where to Store the Event Log?

Any durable storage works — you could use AWS S3, a dedicated event store, or most commonly Apache Kafka (which is built specifically for this). Events are always stored and never deleted.

6

Hydration — Rebuilding State from Events

So we have all events stored. But when a user asks "what's the current status of my video?", we need to compute that. This process is called Hydration.

Hydration = Reading all events in order and re-computing the current state.
Instead of reading a single DB column (e.g., status = "SUCCESS"), you replay the sequence of events and derive what the state must be right now.
💧 Hydration Process — Video Status Query
  User asks: "What's the status of video abc123?"

  Hydration Process starts — reads events in order:

  Event 1: VIDEO_UPLOADED
  → "Ok, video was uploaded" → state = UPLOADED

  Event 2: VIDEO_PROCESSING_STARTED
  → "Ok, processing began" → state = PROCESSING

  Event 3: VIDEO_PROCESSING_PROGRESS (30%)
  → "Still processing..." → state = PROCESSING (30%)

  Event 4: VIDEO_PROCESSING_PROGRESS (70%)
  → "Still processing..." → state = PROCESSING (70%)

  Event 5: VIDEO_PROCESSING_SUCCESS
  → "Processing done!" → state = SUCCESS

  No more events.
  Return to user: "Your video status is SUCCESS ✅"
  (can also show full timeline if user wants!)
✅ Why Hydration is great:
• User can see not just the status, but the full history of what happened
• If something went wrong (stuck at PROCESSING), you can see exactly where it stopped
• No more "why is my video stuck?" mysteries — you have the complete audit trail
• You derive truth from events, not from a DB column that could be stale

Banking Example — Event Sourcing in Action

Let's see Event Sourcing with a bank account balance — one of the most classic examples.

Traditional CRUD Way (loses history)

❌ Traditional — Only stores current balance
  users table:
  | user_id | balance |
  |---------|---------|
  | user_1  |   500   |   ← Initial deposit

  +200 → UPDATE balance = 700
  +300 → UPDATE balance = 1000
  -500 → UPDATE balance = 500

  Final: 500 ✅
  But how did we get to 500? WHO did what? WHEN? ❌ No idea.

Event Sourcing Way (full history)

📜 Event Log — Bank Account
ACCOUNT_OPENED
initial_balance: ₹500 | Jan 1, 9:00 AM
DEPOSIT
amount: ₹200 | Jan 3, 2:00 PM
DEPOSIT
amount: ₹300 | Jan 7, 4:30 PM
WITHDRAWAL
amount: ₹500 | Jan 10, 11:00 AM

Hydration Calculates the Balance

START
Initial balance: ₹500
= ₹500
DEPOSIT +200
Add ₹200
= ₹700
DEPOSIT +300
Add ₹300
= ₹1,000
WITHDRAWAL -500
Subtract ₹500
= ₹500
Final balance: ₹500 — and we know exactly HOW we got there, WHEN each transaction happened, and WHO did what.
🏦
This is literally how real banks work! When you get your bank statement, you don't just see "current balance: ₹500". You see every transaction that led to ₹500. Banks never overwrite — they always append.
8

Replay, Audit Trail & The Time Machine

Since you have ALL events stored, you unlock three superpowers:

🔁 Replay Re-run all events to verify the current state
🔍 Audit Trail Full history of who did what and when
⏱️ Time Machine Know the state at ANY point in the past

Audit Trail

Scenario: A customer calls and says "I never withdrew ₹500, why is my balance ₹500 instead of ₹1000?"

With CRUD: You have no idea. Balance says ₹500, that's all you know. Maybe there was a bug. Maybe they forgot. Can't tell.

With Event Sourcing: You replay all events and show them the exact log — "Here is your WITHDRAWAL event at 11:00 AM on Jan 10, from device X, IP address Y." Full proof.

Time Machine

"What was my balance 1 month ago?"
With CRUD: Impossible — you only have today's balance.

With Event Sourcing: Simply replay only the events that happened before last month's date. The balance at that point in time is the answer. You can reconstruct the state at any moment in history.

Reconciliation

If a user complains "my video is stuck in PROCESSING," you can do Reconciliation — replay all events for that video, find the true current state, and fix the display. No guessing, no manual debugging.

9

Caching the Hydrated State (Optimization)

You might be thinking: "If every read requires replaying thousands of events, won't that be super slow?" Good point! That's why we cache the hydrated state.

⚡ Optimized Event Sourcing with Cache
  Events come in (append-only log)
         │
         ▼
  Hydration Process runs in background
  (reads events → computes current state)
         │
         ▼
  Stores computed state in a fast DB (e.g. PostgreSQL)
         │
         ▼
  When user reads → serve from DB (fast!)
         │
  If user disputes state:
         ▼
  Run Reconciliation → replay events → re-compute
  → update DB with corrected state
Important: The cached DB state is just a read-optimized projection of the events. It's not the source of truth — events are. If the cache gets stale or wrong, you can always fix it by replaying events.

Without Cache (slow)

  • Every read replays all events
  • Gets slower as log grows
  • High latency for users
  • OK for small systems

With Cache (fast)

  • Hydration runs in background
  • Current state stored in fast DB
  • Reads are instant (just query DB)
  • Events still the source of truth

Out-of-Order Events Problem & Kafka Partitions

Here's a sneaky problem: when you have multiple workers consuming from an event stream, events for the same video might be processed out of order.

😱 Out-of-Order Problem
  Event Stream (for video abc123):
  [1] VIDEO_UPLOADED → goes to Worker A (but it's busy!)
  [2] VIDEO_PROCESSING_STARTED → goes to Worker B → processes → sets PROCESSING
  [3] VIDEO_PROCESSING_SUCCESS → goes to Worker C → processes → sets SUCCESS

  (Meanwhile Worker A finally finishes)
  [1] VIDEO_UPLOADED → Worker A processes → sets UPLOADED ← 😱 WRONG!

  Final (wrong) state: UPLOADED
  (Even though the video was actually processed successfully!)
⚠️ The problem: Worker A was slow/busy. It processed Event 1 AFTER Events 2 and 3 were already processed. Now the state is incorrectly set back to UPLOADED even though the video is done.

Solution: Kafka Consumer Groups + Topic Partitions

The Fix: Guarantee that ALL events for a given video always go to the SAME worker. That way, order is always maintained for each video.
🔑 Kafka Partition Solution
  Two videos: Video A and Video B

  Video A events → always go to Partition 0 → Worker 1
  Video B events → always go to Partition 1 → Worker 2

  Rule: A video's ID determines which partition it uses.
  (e.g. hash(videoId) % numPartitions = partition number)

  Now:
  Worker 1 processes ALL of Video A's events in order:
    UPLOADED → PROCESSING_STARTED → SUCCESS ✅

  Worker 2 processes ALL of Video B's events in order:
    UPLOADED → PROCESSING_STARTED → FAILED ✅

  No mixing! No out-of-order! Order is guaranteed!

Kafka Consumer Groups

In Kafka, you create a Consumer Group with multiple workers. Each worker subscribes to specific partitions. Kafka ensures each partition is consumed by only one worker in the group at a time — so events within a partition are always in order.

ConceptWhat it does
TopicA named stream of events (e.g. "video-events")
PartitionA sub-division of a topic — events in a partition are always ordered
Consumer GroupA group of workers that share the work of reading from a topic
Partition KeyThe value used to decide which partition an event goes to (e.g. videoId)
✅ Kafka guarantees: All events with the same partition key (e.g. same videoId) always go to the same partition, and thus the same worker. Order is maintained. No dirty reads.

Amazon Order Tracking — Pure Event Sourcing

📦 Amazon Order — Event Sequence
ORDER_PLACED
orderId: "ORD-001", items: [{…}], amount: ₹1,500
PAYMENT_CONFIRMED
orderId: "ORD-001", transactionId: "TXN-XYZ"

Amazon never stores just status = "DELIVERED". They store every event. So when you open the tracking page, they replay those events and show you every step of the journey.

Key Terms to Remember

📜

Event Log

An append-only record of all events that ever happened. Never modified, never deleted. The single source of truth.

💧

Hydration

The process of reading all events in order and computing the current state. Like pressing play on a recording to see where it ends up.

🔁

Replay

Re-running events for auditing or reconciliation. Used when the cached state is wrong or a user disputes something.

🔍

Reconciliation

When the cached state and the event log disagree, replay events to re-compute and fix the cached state.

⏱️

Time Machine

Replay events only up to a certain date/time to know what the state was at any point in history.

🔑

Kafka Partitions

Ensures all events for the same object (e.g. same video, same order) go to the same worker in the right order. Prevents dirty reads.

⚠️ Important Warning from the video:
Event Sourcing is powerful but it's a big architectural decision. Once you go event-sourcing, your entire system needs to be re-architected around event logs as the source of truth. Going back is very hard. Only choose it when you truly need the audit trail, history, and replay capabilities.
