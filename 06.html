What is Rate Limiting?

Every server is just a machine — it has a CPU, RAM, and a hard limit on how many requests it can handle. If too many requests come in, the server overheats, slows down, and eventually crashes.

🖥️ Server Capacity Example
  Server: 2 vCPU, 4 GB RAM
  Comfortable limit: 100 requests/minute
  Risky zone:        150 requests/minute (performance issues)
  Crash zone:        200+ requests/minute (definite crash)

  These aren't hard cutoffs — they're approximations.
  100 rpm = "safe side". 101 won't instantly crash it.
  But consistently over 150 → problems guaranteed.
Rate Limiting = A layer in your system that controls how many requests are allowed through in a given time window. If a user exceeds the limit, their request is rejected with HTTP status code 429 Too Many Requests.
🚿
Shower analogy: Your overhead tank has 1500 litres. If you open it directly, the water pressure would knock you over! The shower pipe and head control the flow — they let water out at a safe, comfortable rate. A rate limiter does the exact same thing for your server.

Why Rate Limiting?

❌ Without Rate Limiting

  • One abusive user can crash your server
  • DDoS attacks bring the whole system down
  • Costs explode (cloud bills scale with load)
  • All users suffer when one user misbehaves
  • No protection against bot traffic

✅ With Rate Limiting

  • Server stays healthy under any traffic
  • Fair usage — no single user hogs resources
  • DDoS protection at the API layer
  • Cost control — scale only for legit traffic
  • Used by Amazon, Stripe, GitHub APIs

How a Rate Limiter Works (High Level)

🔄 Rate Limiter Request Flow
  User makes a request
          │
          ▼
  ┌─────────────────────┐
  │    Rate Limiter     │  ← Sits between user and server
  │  Config: 100 req/min│
  └──────────┬──────────┘
             │
      ┌──────┴──────────────────┐
      │  Check: Are we within   │
      │  the limit right now?   │
      └──────┬──────────────────┘
             │
     ┌───────┴────────────┐
     │YES: Under limit     │NO: Over limit
     ▼                    ▼
  Forward to Server     Return 429
  → Process request     "Too Many Requests"
  → Send response       → Drop request
                        → User must retry later
HTTP Response for Rate Limited Request
429 Too Many Requests — "Come back later, I'm busy!"

The rate limiter is configured with a policy (e.g. 100 requests per minute). Every incoming request is checked against this policy before it ever reaches the server. If the limit is exceeded, the request is dropped right at the limiter — the server never even sees it.

Now the big question: how does the rate limiter count requests and decide when to drop? There are 5 algorithms for this.

3

Algorithm 1 — Token Bucket

🪣

Token Bucket Algorithm

Most popular • Used by Amazon & Stripe • Memory efficient

A bucket holds tokens. Every request consumes one token. A background refiller continuously adds tokens at a fixed rate. No tokens = request dropped.

How It Works — Step by Step

🪣 Token Bucket — Example (Capacity=5, Refill=3/sec)
  Bucket capacity: 5 tokens
  Refill rate:     3 tokens per second
  Start:           Bucket is empty

  ┌─────────────────────────────────────────────────────┐
  │ Second 1: Refiller adds 3 tokens → [●●●○○] (3/5)   │
  │                                                     │
  │ Request 1 comes in → Take 1 token → [●●○○○] (2/5)  │
  │                    → ✅ ALLOWED                      │
  │ Request 2 comes in → Take 1 token → [●○○○○] (1/5)  │
  │                    → ✅ ALLOWED                      │
  │ Request 3 comes in → Take 1 token → [○○○○○] (0/5)  │
  │                    → ✅ ALLOWED                      │
  │ Request 4 comes in → No tokens!                     │
  │                    → ❌ REJECTED (429)               │
  └─────────────────────────────────────────────────────┘

  ┌─────────────────────────────────────────────────────┐
  │ Second 2: Refiller adds 3 tokens → [●●●○○] (3/5)   │
  │ Request 4 retries → Token available → ✅ ALLOWED    │
  └─────────────────────────────────────────────────────┘

  ┌─────────────────────────────────────────────────────┐
  │ Second 3: No requests → Refiller tries to add 3    │
  │ But bucket is already at 3 → adds to 5 (max = 5)   │
  │ → [●●●●●] (5/5) — bucket never exceeds capacity    │
  └─────────────────────────────────────────────────────┘

✅ Pros

  • Simple to understand and implement
  • Memory efficient
  • Allows short bursts of traffic
  • Used widely in production (Amazon, Stripe)

    • ❌ Cons

  • Two parameters to tune: bucket size + refill rate
  • Tuning them correctly for production is tricky
  • Wrong tuning = too strict or too lenient
    • Two parameters to remember:
    1. Bucket Size (Capacity) — max tokens the bucket can hold
    2. Refill Rate — how many tokens are added per second/minute
    Both must be tuned to match your server's actual capacity.
    🎫
    Think of it like concert tickets: The venue gives out 3 tickets every second (refill rate). Max 5 tickets in the pool at any time (capacity). Each person needs 1 ticket to enter (1 token per request). No tickets = you wait outside.

    Algorithm 2 — Leaky Bucket

    💧

    Leaky Bucket Algorithm

    Uses a queue • Processes at fixed rate • Smooth outflow

    All incoming requests are added to a queue (the "bucket"). Requests leak out of the bottom at a fixed, controlled rate for processing. The bucket absorbs spikes; the server only ever gets a steady stream.

    How It Works — The Shower Analogy

    💧 Leaky Bucket — Visual (Capacity=10,000, Process Rate=5/min)
      20,000 requests/minute coming in (users hammering the API)
          │
          ▼  All requests fall into the bucket (queue)
  ┌───────────────────┐
  │  BUCKET (Queue)   │  ← Max capacity: 10,000
  │  [][][][][][][][] │
  │  [][][][][][][][] │  ← Requests pile up here
  │  [][][][][][][][] │
  └────────┬──────────┘
           │ Leaks at fixed rate (5 req/min)
           │ (hole size = your server's processing rate)
           ▼
      ┌─────────┐
      │  Server │ ← Gets exactly 5 req/min. Calm & steady!
      └─────────┘

  If bucket fills up past 10,000?
  → New requests are DROPPED (429 Too Many Requests)
    🚿
    Exactly like a shower! Your tank has 1500 litres (bucket capacity). The tap is fully open (users sending lots of requests). But the shower head controls the actual flow — water comes out at a comfortable, fixed rate. You enjoy the shower; the tank handles the pressure.

    ✅ Pros

  • Memory efficient with limited queue size
  • Smooth, stable outflow rate
  • Server never gets overwhelmed
  • Perfect for use cases needing steady flow

    • ❌ Cons

  • Burst traffic fills the queue with old requests
  • New requests may starve if queue is full of old ones
  • Two parameters to tune: queue size + drain rate
  • Hit-and-trial tuning in production

    • Token Bucket vs Leaky Bucket

    🪣 Token Bucket

    • Allows short bursts (if tokens available, send fast)
    • Rate varies based on token availability
    • Better for bursty traffic patterns
    • Requests processed as soon as token is available

    💧 Leaky Bucket

    • Fixed, constant processing rate — no bursts
    • Rate is always exactly X requests/period
    • Better for stable, predictable outflow
    • Uses a queue — requests wait their turn

    Algorithm 3 — Fixed Window Counter

    🪟

    Fixed Window Counter Algorithm

    Divide time into fixed windows • Count per window • Reset on new window

    Split the timeline into equal fixed-size windows (e.g. 1 second each). Inside each window, count requests. If count exceeds the threshold, reject. When the window ends, reset the counter.

    How It Works

    🪟 Fixed Window Counter (Limit = 3 req/second)
      Timeline: |── Window 1 ──|── Window 2 ──|── Window 3 ──|
            0s            1s             2s             3s

  Window 1: Request 1 → counter=1 ✅  (1 < 3, allow)
            Request 2 → counter=2 ✅  (2 < 3, allow)
            Request 3 → counter=3 ✅  (3 = 3, allow)
  Window ends → RESET counter to 0

  Window 2: Request 4 → counter=1 ✅  (fresh window!)
            Request 5 → counter=2 ✅
            Request 6 → counter=3 ✅
            Request 7 → counter=4 ❌  (4 > 3, reject 429!)
            Request 8 → counter=4 ❌  (still rejected)

    ⚠️ The Big Bug — Edge Case Problem

    🐛 Fixed Window Edge Case Bug
      Timeline: |──── Window 1 ────|──── Window 2 ────|
            0s               1s                  2s

  At 0.5s (in Window 1): 3 requests processed ✅
  At 1.1s (in Window 2): 1 request processed  ✅ (new window, counter reset!)

  But wait... look at this 1-second window: 0.5s → 1.5s
  ┌──────────────────────────────────┐
  │ 0.5s to 1s (Window 1):  3 req   │
  │ 1.0s to 1.5s (Window 2): 1 req  │
  │ Total in this 1 second:  4 req!  │← MORE than our limit of 3!
  └──────────────────────────────────┘

  The boundary between two windows is a blind spot.
  You can sneak in MORE requests than allowed at window edges!
    ⚠️ The Fundamental Bug: At the boundary between two windows, a user can send requests at the end of Window 1 AND the start of Window 2. Combined, they may exceed the limit in a single real second — even though each window looks fine individually. This is called the edge case / spike at boundaries.

    ✅ Pros

  • Very simple to implement
  • Memory efficient (just one counter)
  • Resets cleanly at window boundary
  • Small burst at edges usually OK in practice

    • ❌ Cons

  • Edge case: 2× the limit possible at boundary
  • Not accurate at second-level granularity
  • Can be exploited by timing requests at boundaries

    Algorithm 4 — Sliding Window Log

    📜

    Sliding Window Log Algorithm

    Fixes Fixed Window's edge bug • Keeps a timestamp log • Most accurate

    Instead of a counter, keep a log (list) of timestamps of every request. When a new request arrives, remove all expired timestamps (outside the window), then check if the log size is still within the threshold.

    How It Works — Step by Step

    📜 Sliding Window Log (Limit = 3 req per 5 seconds)
      Threshold: 3 requests per 5-second window

  t=1s: Request comes in
        Log: [1s]        → count=1, (1 ≤ 3) → ✅ ALLOWED

  t=3s: Request comes in
        Log: [1s, 3s]    → count=2, (2 ≤ 3) → ✅ ALLOWED

  t=4.5s: Request comes in
        Log: [1s, 3s, 4.5s] → count=3, (3 ≤ 3) → ✅ ALLOWED

  t=6s: Request comes in
        Window is 5s, so we remove timestamps older than 6-5=1s
        → Remove t=1s (expired!)
        Log: [3s, 4.5s, 6s] → count=3, (3 ≤ 3) → ✅ ALLOWED

  t=7s: Two requests come in
        Remove t=2s window start (6-5=2s), t=3s still alive since 3>2
        Log: [3s, 4.5s, 6s] → count=3 already
        New request → count would be 4 → ❌ REJECTED!
        Another request → count would be 4 → ❌ REJECTED!

  t=8s: Request comes in
        Remove expired timestamps older than 8-5=3s
        → Remove t=3s (expired!)
        Log: [4.5s, 6s, 8s] → count=3, (3 ≤ 3) → ✅ ALLOWED
    ✅ No edge case bug! Because the window is always computed relative to NOW (not a fixed slot), there's no blind spot at boundaries. The window slides forward with every request check.
    How it's stored: Timestamp data is usually kept in a cache (like Redis sorted sets). The key is the user ID, and the values are timestamps of recent requests.

    ✅ Pros

  • Very accurate — no edge case bug
  • Window always reflects the last N seconds exactly
  • Fair to all users regardless of timing

    • ❌ Cons

  • Memory intensive — store timestamp per request
  • Even rejected requests consume log space
  • More complex to implement than fixed window

    Algorithm 5 — Sliding Window Counter (Hybrid)

    ⚗️

    Sliding Window Counter Algorithm

    Hybrid of Fixed Window + Sliding Window Log • Best balance of accuracy and memory

    Uses fixed windows (for counters) but approximates a sliding window by weighting the previous window's count proportionally. Best of both worlds!

    The Core Idea

    ⚗️ Sliding Window Counter — The Formula
      Threshold: 3 requests per second

  ┌──────────────────────────────────────────────────────┐
  │   Window 1 (0s–1s)     │    Window 2 (1s–2s)        │
  │   Count = 3            │    Count so far = 1         │
  └──────────────────────────────────────────────────────┘

  A new request arrives at t=1.3s
  → It's 30% into Window 2 (0.3s into a 1s window)
  → That means 70% of Window 1 is still "relevant"

  Effective Count = (Window 1 count × 70%) + Window 2 count
                 = (3 × 0.70) + 1
                 = 2.1 + 1
                 = 3.1  → Exceeds threshold of 3 → ❌ REJECT!

  Another scenario: request at t=1.8s (80% into Window 2)
  → Only 20% of Window 1 is relevant
  Effective Count = (3 × 0.20) + 0
                 = 0.6 + 0 = 0.6 → Well under 3 → ✅ ALLOW!
    The formula:
    Effective Count = (Prev Window Count × (1 - % through current window)) + Current Window Count

    The closer you are to the end of the current window, the less weight the previous window carries. This creates a smooth, sliding effect without storing individual timestamps.
    🎚️
    Think of it like a volume fade: As you move further into the current window, the previous window's count "fades out" like a volume knob turning down. At 0% through current window, previous counts 100%. At 100% through current window, previous counts 0%.

    ✅ Pros

  • Much more accurate than Fixed Window
  • Memory efficient — only two counters needed
  • Handles edge case much better
  • Great balance of accuracy vs complexity

    • ❌ Cons

  • Still an approximation (not 100% exact)
  • Slightly more complex than Fixed Window
  • Edge cases with very high burst traffic still possible

    Which Algorithm Should You Use?

    🪣 Use Token Bucket when...

    • You want to allow short traffic bursts
    • You need simplicity
    • API rate limiting (per user, per key)
    • Most common choice for APIs

    💧 Use Leaky Bucket when...

    • You need a perfectly stable outflow rate
    • Processing must be smooth and predictable
    • Network traffic shaping
    • Queue-based systems

    🪟 Use Fixed Window when...

    • Simplicity is the priority
    • Slight over-limit at boundary is acceptable
    • Low traffic, simple use cases
    • Not recommended for high accuracy needs

    📜 Use Sliding Window Log when...

    • Accuracy is critical (financial APIs, compliance)
    • Memory cost is acceptable
    • You must never allow even 1 extra request
    • Low traffic, strict rules

    📖 Quick Recap — All 5 Algorithms

    🪣

    Token Bucket

    Refiller adds tokens. Request takes token. No token = drop. Allows bursts.

    💧

    Leaky Bucket

    Requests queue up. Drain at fixed rate. Queue full = drop. Smooth outflow.

    🪟

    Fixed Window

    Count requests per time slot. Reset counter each window. Simple but has edge bug.

    📜

    Sliding Window Log

    Store all timestamps. Remove expired. Count remaining. Most accurate, most memory.

    ⚗️

    Sliding Window Counter

    Hybrid: Fixed windows + weighted formula. Great balance of accuracy and efficiency.

    🚫

    HTTP 429

    "Too Many Requests" — what every rate limiter returns when a request is dropped.

    📌 Remember: In real production systems, rate limiting is typically done per user (by user ID or API key), not globally. This way, one abusive user doesn't affect everyone else. Tools like Redis are used to store the counters/logs because they're fast (in-memory) and support atomic operations (no race conditions).
