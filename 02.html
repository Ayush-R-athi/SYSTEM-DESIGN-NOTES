The Golden Rule of System Design

Before diving in, there's one thing to always remember:

System Design is never one-size-fits-all.
Every company has a different use case, different traffic pattern, and different priorities. A system that works perfectly for Netflix will crash YouTube, and vice versa. System design evolves over time with experience.

The goal of system design is always a balance of three things:

🛡️ Fault Tolerant

  • System shouldn't crash under heavy load
  • Should recover from failures

⚡ Scalable

  • Should handle sudden spikes
  • Should scale up and down smoothly

💰 Cost Optimized

  • Don't over-provision resources
  • Pay only for what you use
📈
Scaling is easy if money is no object. Just throw 10× the servers at it. But real engineering is finding the optimal balance — enough to handle the load, without wasting money on idle resources.

Traffic Patterns — Why They Matter

The biggest challenge in scaling is knowing when to scale. Traffic is not always steady — it spikes and drops. Understanding your traffic pattern is the foundation of good system design.

📈 Gradual Growth (Easy to handle)

  • Traffic increases slowly over days/weeks
  • Auto-scaling policies have time to react
  • Add 1 server at a time as CPU crosses 70%
  • Very manageable

⚡ Sudden Spike (Hard to handle)

  • Traffic jumps 10× in seconds
  • Auto-scaling can't react fast enough
  • Average CPU metric takes time to update
  • System crashes before new servers boot up
📉 What Happens During a Sudden Spike
  Normal traffic (3 servers running)
         |
         |  Spike! 10× traffic in seconds
         |
         ▼
  CPU Avg policy says "add 1 server"
  (but avg is still being calculated...)
         |
         ▼
  2 existing servers get overwhelmed
         |
         ▼
  💥 CRASH — existing servers go down
         |
         ▼
  New server is still booting...
  (too late, users already left!)
Key insight: Auto-scaling works on averages. Averages take time. But sudden spikes don't wait. This is why traffic pattern prediction is so important.

Netflix vs YouTube vs Hotstar — Case Study

All three are video streaming platforms. But their traffic patterns are completely different — so their system designs must be different too.

🎬 Netflix

  • Content is released by Netflix themselves
  • Movie launch dates are known weeks ahead
  • Traffic spike is predictable
  • Can pre-scale 24 hrs before launch
  • Can pre-cache movie on CDN edge servers
  • Easiest to manage

📺 YouTube

  • Anyone can publish content
  • Mr Beast going live? No warning!
  • Breaking news? No warning!
  • Traffic is unpredictable
  • Must stay pre-warmed at all times
  • Most expensive to operate

🏏 Hotstar

  • Mix of movies + live cricket
  • Match dates known in advance
  • But traffic during match is wild!
  • Spikes on every wicket, every boundary
  • Must disable auto-scaling during match
  • Most complex pattern

🏏 The Hotstar Cricket Match Deep Dive

📊 Hotstar Traffic Pattern During a Cricket Match
  Before match: Normal traffic (movies service active)
       |
       │ Toss time → Spike ↑ (everyone tunes in)
       |
       │ Match starts, boring overs → Dip ↓
       |
       │ Wicket falls → Spike ↑ (WhatsApp buzzing!)
       |
       │ Not interesting → Dip ↓
       |
       │ Virat Kohli comes to bat → Big Spike ↑↑
       |
       │ Kohli out first ball → Another spike ↑ (rage)
       |
       │ People go back → Back button dbao → 
       │ Now MOVIES API gets hit! ← 24 crore people!
       |
  After match: Scale down
⚠️ The "Back Button" problem (Hotstar's lesson):
When 24 crore people are watching live cricket and they press Back, they land on the movies homepage — which calls the Movies API. So even though Movies is at low traffic during the match, it can get hit with 24 crore requests in one second! You must keep the Movies service scaled up too during the match.

Netflix — How to Handle Predictable Spikes

Netflix's smart approach:
✅ Pre-scale: 24 hours before a movie launch, scale from 10 → 30 servers
✅ Pre-cache: Push first 10 minutes of the movie to all CDN edge servers worldwide before launch
✅ If the movie flops (no traffic), scale back down — no harm done
✅ Cost is predictable and controlled

Hotstar — Why to DISABLE Auto-Scaling During a Match

❌ Don't use auto-scaling during a cricket match!
During a match, traffic goes up and down every few seconds (wickets, boundaries, boring overs). If auto-scaling is ON:
• Traffic dips → servers scale down
• Next second, wicket falls → traffic spikes
• New servers are still booting → crash!

✅ Better approach: Keep 200 servers running for the full 4 hours of the match. Yes it costs more, but your system stays stable. Fault tolerance > cost savings during critical events.

NetflixPredictable spikes (movie launch)Pre-scale + Pre-cache CDNYes, with manual override
YouTubeCompletely unpredictableAlways pre-warmed, large bufferLimited — always hot
HotstarPredictable start, wild during matchPre-scale all services, disable auto-scale during matchOFF during match

Auto Scaling Policies

Auto-scaling doesn't happen by magic. You have to set a policy — a rule that tells the system when to add or remove servers.

⚙️ Common Auto Scaling Policy Examples
  Policy 1 (Request-based):
  "If requests in last 15 mins > 1000,
   spin up 1 more server"

  Policy 2 (CPU-based):
  "If average CPU usage > 70%,
   spin up 1 more server"

  Policy 3 (Memory-based):
  "If average RAM usage > 70%,
   spin up 1 more server"

  Policy 4 (Scheduled):
  "At 11:00 PM every night before
   the sale, scale to 30 servers"
   ← This is what Netflix/Amazon does!
Important: CPU/memory based policies work great for gradual traffic growth. For sudden spikes, scheduled pre-scaling is more reliable because it doesn't wait for averages to update.

Serverless Architecture — AWS Lambda

Managing servers is complex — you have to worry about CPU, RAM, OS, auto-scaling policies, IP allocation, load balancer registration... What if you could skip all of that and just write code?

That's exactly what Serverless (AWS Lambda) does. The name is a bit misleading — there IS a server, but you don't manage it.

⚡ How Lambda Works
  You: Write a JS/Python function
       (just a file with code!)
         |
         ▼
  Upload it to AWS Lambda
         |
         ▼
  AWS gives you a public URL:
  https://abc.execute-api.amazonaws.com/
         |
         ▼
  Request comes in
         |
         ▼
  Lambda spins up a tiny function instance
  → processes request
  → returns response
  → self-destructs (gone!)

  10 requests come in simultaneously?
  → 10 Lambda instances spin up in parallel
  → All 10 process their request
  → All 10 self-destruct

Pricing — Very Cheap!

AWS Lambda Free Tier:
✅ First 1 million requests/month — FREE
✅ 3.2 million seconds of compute — FREE
✅ After that: only $0.20 per additional million requests

No users → No cost. Users come → Pay only for what runs.

Pros and Cons of Serverless

✅ Pros

  • No server management at all
  • No auto-scaling config needed
  • Very cheap (pay per invocation)
  • No idle cost (0 users = $0)
  • Scales automatically to any traffic
  • Focus on code, not infrastructure

    • ❌ Cons

  • Cold Start problem
  • Max 15 second execution limit
  • Always stateless (can't store data)
  • DDoS can run up massive bills
  • Vendor lock-in (AWS ecosystem)
  • No OS-level configuration possible
  • DB connection problems at scale

    • The Cold Start Problem Explained

    🥶 Cold Start vs Warm Start
      Scenario: No users for several hours

  First user arrives at 9:00 AM:
       |
       ▼
  Lambda has to:
  1. Pull your code from storage
  2. Set up environment
  3. Process request
  Time taken: ~2 seconds ← COLD START

  Second user arrives 1 second later:
       |
       ▼
  Lambda is already warm!
  Code is already loaded.
  Time taken: ~0.1 seconds ← WARM

  Hundreds of users:
  → All subsequent lambdas spin up fast
  → Only the very FIRST request is slow
    Cold start only matters if you have long gaps with zero traffic. If your site always has at least a few users, Lambda stays warm and it's never a problem.

    The Vendor Lock-In Trap

    ⚠️ The AWS Ecosystem Trap:
    Start with Lambda → then need SQS (queue) → then API Gateway → then Route 53 (DNS) → then S3 (storage) → then CloudWatch (logs) → then Step Functions (long tasks)...

    Before you know it, your entire system is built on AWS services. AWS is cheap now, but if they raise prices, you have no choice. Migrating means rewriting everything.

    The "Works on My Machine" Problem

    This is one of the most famous and frustrating problems in software development. You build something on your laptop, it works perfectly. You deploy it to the server — and it breaks.

    😤 Why Does This Happen?
      Your Laptop (Windows/Mac):
  ├── ffmpeg version 0.4.2 installed
  ├── Python 3.9
  ├── Node 18
  └── 30 other libraries (specific versions)
  → Code works ✅

  Production Server (Linux Ubuntu):
  ├── ffmpeg version 0.3.8 (different!)
  ├── Python 3.8 (different!)
  ├── Node 16 (different!)
  └── Some libraries missing!
  → Code breaks ❌

    For a real project, you might have 30-40 packages with specific version requirements. Making sure all of them match exactly across your laptop and multiple server replicas is a nightmare.

    🍱
    Analogy: Imagine you cook a perfect meal in your kitchen. You write the recipe. But the other kitchen has different utensils, different spices, even a different type of oven. The same recipe may not produce the same dish!

    Virtualization — The First Solution (VMs)

    The first attempt to solve "works on my machine" was Virtual Machines (VMs). The idea: bundle your entire environment (OS + libraries + code) into one package.

    🖥️ How VMs Work
      Your Laptop (Host OS: Windows)
  └── Virtual Machine (Guest OS: Ubuntu)
      ├── ffmpeg 0.4.2 installed
      ├── All your libraries installed
      └── Your code

  You test everything inside the VM.
  It works!

  You export this VM image.
  You deploy it to the server.
  Server runs the same VM image.
  → Code works on server too ✅

  Scale out? Deploy same VM image
  to more servers. Same environment!

    ✅ VM Solved

    • "Works on my machine" problem — gone!
    • Same environment everywhere
    • Consistent across all servers

    ❌ VM Problems

    • Very heavy (full OS inside OS)
    • VM image is 4-5 GB in size
    • Slow to start up
    • Wastes resources (double OS)
    • Scaling is still slow
    🏠
    VM Analogy: Instead of shipping just your recipe, you ship an entire fully-equipped kitchen inside a shipping container. It solves consistency but the container is huge and heavy!
    8

    Containerization — Docker

    Google faced the same problem at massive scale. Their solution: what if we make VMs lighter by removing the biggest part — the full OS?

    The key insight: The host machine already HAS an operating system (OS kernel). Why install another full OS inside your VM? Let the container share the host OS kernel, and only bundle your libraries + code. That's a container!
    📦 VM vs Container — Size Comparison
      Virtual Machine (VM):
  ├── Full OS (Ubuntu) → 4,000 MB
  ├── Libraries (ffmpeg etc.) → 200 MB
  └── Your code → 50 MB
  Total: ~4,250 MB per VM 🐘 HEAVY

  Container:
  ├── (shares host OS kernel — not included!)
  ├── Libraries (ffmpeg etc.) → 200 MB
  └── Your code → 50 MB
  Total: ~250 MB per container 🪶 LIGHT!

  One physical machine can run:
  VMs: maybe 2-3 (they're huge)
  Containers: 15-20+ (they're tiny!)

    Why Containers Changed Everything

    Old Way (VMs / Bare Metal)

    • New server = minutes to boot
    • Install dependencies = more minutes
    • 4 GB+ per instance
    • Can run 2-3 per machine
    • Slow to scale out

    New Way (Containers)

    • Container starts in seconds
    • All deps already in image
    • ~250 MB per container
    • Run 15-20+ per machine
    • Scale out in seconds
    ✅ Containers solve BOTH problems:
    1. "Works on my machine" → Build image once, runs the same everywhere
    2. Slow scaling → Containers start in seconds (not minutes like VMs)
    3. Cost efficient → Pack many containers on one physical machine

    How Docker Works (Simple Version)

    🐳 Docker Workflow
      Step 1: Write a Dockerfile
  (instructions: "use Ubuntu base,
   install ffmpeg, copy my code")

  Step 2: Build Docker Image
  $ docker build -t my-app .
  → Creates a snapshot: OS-less VM
    with your code + dependencies

  Step 3: Run container locally, test it
  $ docker run my-app
  → Works ✅

  Step 4: Push image to registry
  $ docker push my-app

  Step 5: On any server, pull + run
  $ docker pull my-app
  $ docker run my-app
  → Same environment, works everywhere ✅

  Scale out: just run more containers!
  $ docker run my-app (again and again)

    Container Orchestration — Kubernetes

    Containers are great. But when you're running 50+ containers across multiple servers, you need a brain to manage them all. Who creates new containers when traffic spikes? Who deletes them? Who restarts crashed containers?

    That's what Container Orchestration solves. And the most popular tool for this is Kubernetes (K8s).

    The Origin Story of Kubernetes

    Google hits scaling problems (2000s)

    Google is running thousands of servers. Managing containers manually is impossible. They build an internal tool called Borg — a cluster management system to handle all their containers.

    Borg works great (internally)

    Borg handles Google's massive scale. But it stays internal. Other companies face the same container management problem and have no solution.

    Google builds "Project X" (2013)

    The team that built Borg is asked to rewrite it from scratch, applying all their learnings. Goal: a universal container orchestrator that works for any company.

    Kubernetes is born and open-sourced (2014)

    Project X becomes Kubernetes (Greek for "helmsman/captain"). Google donates it to the CNCF (Cloud Native Computing Foundation). It's now open source and maintained by the global community.

    Kubernetes = Borg's lessons, rewritten for everyone.
    Built by Google, donated to the world. Now the industry standard for container orchestration.

    What Kubernetes Does for You

    Without Kubernetes

    • Manually track which container is on which server
    • Manually restart crashed containers
    • Manually scale up/down during traffic changes
    • Manually handle new code deployments
    • Risk of downtime during updates

    With Kubernetes

    • K8s auto-tracks all containers
    • Auto-restarts crashed containers
    • Auto-scales based on rules
    • Rolling updates with zero downtime
    • Built-in load balancer

    Key Kubernetes Concepts

    ConceptWhat it is
    ClusterA group of servers (nodes) managed by Kubernetes
    NodeOne physical/virtual machine in the cluster
    PodThe smallest unit — wraps one or more containers
    Control PlaneThe brain — makes decisions about the cluster
    SchedulerDecides which node a new pod should run on
    KubeletAgent on each node that talks to the control plane
    etcdKey-value store — holds all cluster state/data
    API ServerThe front door of Kubernetes — all commands go through it
    Ingress ControllerHandles external traffic routing (like an API Gateway)

    Deployment Strategies in Kubernetes

    🔄 Rolling Update

    • Replace containers one at a time
    • Old container removed, new one added
    • Zero downtime — some run old, some new
    • Gradual rollout
    • Most common strategy

    🔵🟢 Blue-Green Deployment

    • Run two complete environments (Blue = old, Green = new)
    • Test Green fully while Blue handles traffic
    • Switch all traffic to Green at once
    • Instant rollback — just switch back to Blue
    • Costs more (double the resources)
    🔄 Rolling Update Visualized

  Rolling update begins:
  [New v2] [Old v1] [Old v1] [Old v1] [Old v1]

  [New v2] [New v2] [New v2] [Old v1] [Old v1]
  [New v2] [New v2] [New v2] [New v2] [Old v1]

  After update complete:
  [New v2] [New v2] [New v2] [New v2] [New v2]

  Users never saw downtime! ✅

    Load Testing & Stress Testing

    What big companies like Hotstar do before a big match:
    They send fake traffic to their own servers the day before — simulating the expected load. This is called Load Testing and Stress Testing.

    • Load Test: Simulate expected traffic (e.g. 24 crore users)
    • Stress Test: Push beyond limits to find the breaking point

    This way, they discover failures in advance and fix them before the real event.

    Evolution Timeline & Full Summary

    Here's how deployment technology evolved over time:

    Era 1: Bare Metal Servers

    Direct deployment on physical machines. Fast but environment inconsistencies caused "works on my machine" problems. Slow to scale — setting up a new machine takes hours (install OS, install dependencies, install code...).

    Era 2: Virtual Machines (VMs)

    Bundle full OS + dependencies + code into one portable image. Solved the consistency problem! But VMs are 4-5 GB each, slow to start, resource heavy. One physical machine can run very few VMs.

    Era 3: Containers (Docker)

    Remove the OS from the image — share host OS kernel. Now only 200-300 MB per container. Starts in seconds. Pack 15-20 containers on one machine. Solved both consistency AND scaling speed. Google pioneered this internally.

    Era 4: Container Orchestration (Kubernetes)

    With 50+ containers across multiple servers, you need a brain. Kubernetes auto-manages creation, deletion, health checks, scaling, updates. Rolling updates + blue-green deployments = zero downtime. Google open-sourced this as Kubernetes in 2014.

    Era 5: Serverless (Lambda)

    Don't even think about containers — just write code. AWS manages everything. Pay only per request. Amazing for unpredictable or low traffic. But: cold starts, 15s limit, vendor lock-in, stateless only. Best for simple functions, not large stateful apps.

    Quick Reference — When to Use What

    TechnologyBest ForMain Trade-off
    Bare MetalMaximum performance, full controlSlow to scale, "works on my machine" problem
    VMsStrong isolation, full OS control neededHeavy (4+ GB), slow startup
    Containers (Docker)Consistent, fast, scalable deploymentsNeed orchestration tool at scale
    KubernetesManaging containers at scale, zero-downtime deploymentsComplex to set up and learn
    Serverless (Lambda)Event-driven, unpredictable traffic, low overheadCold starts, vendor lock-in, 15s limit, stateless

    📖 Key Terms to Remember

    🐳

    Docker

    The tool that creates and runs containers. Packages code + dependencies (without OS) into a portable image.

    ☸️

    Kubernetes (K8s)

    The brain that manages containers across a cluster of servers. Auto-scaling, auto-healing, rolling updates.

    ⚡

    Serverless / Lambda

    Write code, AWS runs it. No server management. Pay per invocation. Best for simple, stateless functions.

    📊

    Traffic Pattern

    How traffic changes over time for your app. Predictable (Netflix) vs unpredictable (YouTube) changes your entire design.

    🔄

    Rolling Update

    Replace containers one at a time so users never see downtime during a code deployment.

    🔵🟢

    Blue-Green Deploy

    Run old + new environments in parallel. Switch all traffic instantly. Easy rollback.

    🥶

    Cold Start

    The delay when a Lambda function is invoked after a long idle period. First request is slow; after that it's warm.

    🔒

    Vendor Lock-In

    When you're so deep into one cloud provider's ecosystem that switching providers would require rewriting everything.
