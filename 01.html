Client & Server — The Basics

At the highest level, every system has just two things:

📱 Client
(Mobile / Laptop / IoT)
⟷
🖥️ Server
(Machine with Public IP)
Client = Anyone using your app (phone, laptop, browser).
Server = A machine that runs 24/7 and has a public IP address so the world can reach it.
☁️
Cloud is not magic — it's someone else's machine.
AWS, DigitalOcean etc. just give you a virtual machine that runs 24/7 with a public IP. You could use your own laptop as a server too, but nobody wants that!

IP Address & DNS

Every server on the internet has an IP address (like 10.2.3.4). But numbers are hard to remember — nobody remembers phone numbers either!

That's why we use Domain Names like amazon.com. The system that translates domain names → IP addresses is called DNS.

How DNS Resolution Works

🔄 Request Flow — DNS Resolution
  You type amazon.com
         |
         ▼
  ┌─────────────┐      "What's the IP
  │  DNS Server │◄──── for amazon.com?"
  │  (Directory)│
  └─────────────┘
         |
         │  Returns: 10.2.3.4
         ▼
  Your browser now connects
  directly to IP 10.2.3.4
         |
         ▼
  ┌─────────────┐
  │   Server    │ ──► Sends back the webpage
  └─────────────┘
DNS = Phone book of the internet.
It maps amazon.com → 10.2.3.4. When you buy a domain and point it to your server, you're updating this phone book.
🏠
IP address is like your home address.
Street name, house number, city, pincode, state, country — all of these together help someone find you. An IP does the same for servers.

Vertical Scaling (Scale Up)

Imagine your server starts with 2 CPU 4 GB RAM. As more users come, the server gets overwhelmed and crashes.

The first instinct? Make the server bigger! Add more CPU and RAM to the same machine.

Before (Small Server)

  • 2 CPU, 4 GB RAM
  • Can handle small traffic
  • Crashes under load

After (Vertical Scale Up)

  • 64 CPU, 128 GB RAM
  • Handles much more traffic
  • Still has a limit!
⚠️ Problems with Vertical Scaling:
1. Downtime required — You can't add CPU/RAM to a running machine. It needs a restart. Even 1 minute of downtime costs Amazon millions.
2. Resource waste — You set up the machine for peak traffic, but 90% of the time you're only using 10% of it. Money wasted!
3. Hard limit — You can't upgrade forever. There's a physical limit.
🍳
Restaurant analogy: If you usually have 2 cooks but sometimes rush comes, you could hire 10 full-time cooks. But you pay 10 salaries even when there's no rush. That's wasteful — vertical scaling is similar.
✅ Cloud solves waste problem — AWS lets you say "start with 2 CPU, but auto-scale up when traffic increases, and scale down when it drops." You only pay for what you use.
4

Horizontal Scaling (Scale Out)

Instead of making one server bigger, what if you just add more servers?

📐 Horizontal Scaling
  Instead of 1 big machine:

  ┌──────────┐
  │ Server 1 │  IP: 10.2.3.5
  └──────────┘

  You have multiple identical machines:

  ┌──────────┐     ┌──────────┐     ┌──────────┐
  │ Server 1 │     │ Server 2 │     │ Server 3 │
  │ IP: ...5 │     │ IP: ...6 │     │ IP: ...7 │
  └──────────┘     └──────────┘     └──────────┘

Vertical Scaling

  • 1 big server
  • Needs downtime to upgrade
  • Has a physical limit
  • Wastes resources off-peak
  • No load balancer needed

Horizontal Scaling

  • Many smaller servers
  • No downtime (add new servers while old ones run)
  • No hard limit (keep adding)
  • Scale down when quiet
  • Needs a Load Balancer
🍳
Better restaurant analogy: You hire extra cooks per hour only when rush comes. When rush ends, they go home. You pay only for the hours worked. That's horizontal scaling!

Load Balancer

With multiple servers, there's a problem: who decides which server handles which request? DNS can only point to one IP. That's where a Load Balancer comes in.

🔄 Load Balancer Flow
  User types amazon.com
         |
         ▼
  DNS returns Load Balancer IP (10.2.3.7)
         |
         ▼
  ┌───────────────────┐
  │   Load Balancer   │  ← Registered in DNS
  │   IP: 10.2.3.7    │
  └───────────────────┘
         |
    Distributes traffic
    /       |       \
   ▼        ▼        ▼
┌──────┐ ┌──────┐ ┌──────┐
│Srv 1 │ │Srv 2 │ │Srv 3 │
└──────┘ └──────┘ └──────┘

How does it distribute traffic? (Round Robin)

The simplest method is Round Robin: request 1 → Server 1, request 2 → Server 2, request 3 → Server 3, request 4 → Server 1 again... and so on.

Load Balancer Intelligence: Before sending traffic to a new server, the LB checks if it's healthy (up and running for at least 1 minute). Only then does it route traffic there. In AWS, this is called ELB (Elastic Load Balancer).

Scale Out & Scale In

Scale Out (add servers)

  • New server boots up
  • Register with load balancer
  • LB health checks it
  • Traffic starts flowing to it

Scale In (remove servers)

  • Traffic reduces (e.g. sale is over)
  • Remove extra servers
  • Tell LB you have fewer servers
  • Save money!

API Gateway & Microservices

In a real app like Amazon, you don't have just one server. You have many separate services (called Microservices) — Auth, Orders, Payments, API, etc. Each service runs on its own servers.

Problem: How do you route /auth requests to Auth servers, /orders to Order servers, etc.?

Answer: API Gateway

🗺️ API Gateway Routes Traffic to the Right Service
  User makes a request
         |
         ▼
  ┌─────────────────┐
  │   API Gateway   │  ← Single entry point
  │  IP: 10.5.8.3   │    (Registered in DNS)
  └─────────────────┘
         |
    ┌────┴────────────────┐
    │ RULES:              │
    │ /auth    → Auth LB  │
    │ /orders  → Order LB │
    │ /payment → Pay LB   │
    └────┬────────────────┘
         |
  ┌──────┴──────────────────────────┐
  |             |                   |
  ▼             ▼                   ▼
Auth LB      Order LB           Payment LB
  |             |                   |
Auth         Order              Payment
Servers      Servers            Servers
(×4)         (×3)               (×2)
URL PathRoutes ToWhy
/authAuth Service Load BalancerLogin/signup requests
/ordersOrders Service Load BalancerOrder management
/paymentsPayments Service Load BalancerPayment processing
/apiMain API Load BalancerGeneral API calls
API Gateway definition: It's the single entry point (like a reception desk). Every request comes here first, it checks the URL, and forwards the request to the right service. It can also do authentication — check if the user is logged in before forwarding.

Queue Systems & Async Processing

When a user makes a payment, you might want to send them an email. The wrong way is to have the Payment service directly call the Email service and wait — this is Synchronous.

❌ Synchronous (Bad)

  • Payment calls Email service
  • Waits for email to be sent
  • If Gmail is slow, payment is slow
  • Not scalable
  • Tightly coupled

✅ Asynchronous (Good)

  • Payment drops message in Queue
  • Returns immediately (fast!)
  • Email Worker reads queue later
  • Highly scalable
  • Loosely coupled

How a Queue Works

📬 Queue (SQS) — First In, First Out
  Payment Service                Queue (SQS)         Email Worker
       |                     ┌──────────────┐              |
       │ Order #1 happened   │ [Order#1]    │              |
       │────────────────────►│ [Order#2]    │              |
       │ Order #2 happened   │ [Order#3]    │              |
       │────────────────────►│ [Order#4]    │              |
       │                     └──────────────┘              |
       │                            |          pulls event  |
       │                            │◄─────────────────────│
       │                            │  sends email         |
       │                            │─────────────────────►│
       │                                                   |
  Done! (no waiting)             Queue is                 Sends emails
                                 decoupled                one by one
AWS SQS = Simple Queue Service. This is Amazon's managed queue. Workers can poll (ask) the queue for messages to process.

Pull vs Push

Pull (Polling)

  • Worker asks queue: "Any messages?"
  • Short poll: ask every 1 second
  • Long poll: wait 10 seconds for messages, then batch pull
  • SQS uses this method

Push

  • Queue calls/invokes your worker
  • Worker doesn't need to check
  • Queue pushes when event arrives
  • Used by some serverless setups
Extra benefit — Rate Limiting with Gmail: If Gmail only allows 10 emails/second, configure your Email Worker to never pick more than 10 messages per second. The queue will hold the rest. No complaints from Gmail!

Pub/Sub & Fan-Out Architecture

Queue (SQS) is 1-to-1: one message → one consumer picks it. But what if ONE payment event should trigger FOUR things: WhatsApp, Email, SMS, and Vendor notification?

You need Pub/Sub (Publish-Subscribe).

SNS — Simple Notification Service

📢 Pub/Sub with SNS
  Payment happens
         |
         ▼
  ┌─────────────┐     "Payment done!"
  │     SNS     │ ────────────────────────────────────┐
  │ (Publisher) │                                     |
  └─────────────┘                                     |
         |                                            |
    Broadcasts to ALL subscribers                     |
    /            |            \                       |
   ▼             ▼             ▼                      ▼
Email Worker  WhatsApp      SMS Worker        Vendor Email
(receives     Worker        (receives         Worker
 it)          (receives      it)              (receives it)
              it)
⚠️ Problem with pure SNS: There's no guarantee. If a subscriber was offline when you published, the message is gone! No retry, no acknowledgement.

Fan-Out Architecture = SNS + SQS combined

⚡ Fan-Out: Best of Both Worlds
  Payment happens
         |
         ▼
  ┌──────────┐
  │   SNS    │ ← Publishes event once
  └──────────┘
         |
   ┌─────┼──────┐
   ▼     ▼      ▼
  SQS   SQS    SQS   ← Each gets a copy
  [WA]  [Email][SMS]
   |      |     |
   ▼      ▼     ▼
  WA    Email   SMS  ← Each has its own workers
  Worker Worker Worker ← Can retry independently!
✅ Fan-Out benefits:
• Multiple services get notified (like SNS)
• Each has its own queue, so retries work (like SQS)
• If SMS fails, only SMS retries — WhatsApp and Email are fine!
📢
Real-world example: When you upload a YouTube video, one event fans out into: transcoding to 480p, 1080p, 4K, extracting audio, generating thumbnail, transcribing captions — all happening in parallel!
FeatureSQS (Queue)SNS (Pub/Sub)Fan-Out (SNS+SQS)
Consumers1 (only one picks)Many (all get it)Many (all get it)
Retry✅ Yes❌ No✅ Yes (per queue)
Acknowledgement✅ Yes❌ No✅ Yes
Use caseOne task per eventBroadcast notificationMultiple tasks + reliability

Rate Limiting

Users can overload your system with too many requests — or worse, hackers can launch a DDoS attack. Rate limiting says: "You can only send X requests per second. After that, you're blocked."

Rate Limiting = Controlling how many requests are allowed in a given time period.
If you exceed the limit, you get HTTP 429: Too Many Requests.

Common Rate Limiting Algorithms

Token Bucket

  • Bucket fills with tokens over time
  • Each request uses one token
  • No tokens = request blocked
  • Allows bursts of traffic

Leaky Bucket

  • Requests go into a "bucket"
  • Bucket "leaks" at a fixed rate
  • Overflow = requests dropped
  • Smooth, consistent output rate
Rate limiting isn't just for users. You also rate-limit internally — e.g. your Email Worker is rate-limited to 10/sec so you don't exceed Gmail's API limits.

Database Scaling & Caching

Your microservices all query the same database. As services grow, the DB gets overwhelmed. How do you scale it?

Read Replicas

📊 Primary + Read Replicas
                    ┌──────────────────┐
  ALL WRITES ──────►│ Primary DB Node  │
  Real-time reads   │  (Master Node)   │
                    └────────┬─────────┘
                             │ Syncs data (slight delay)
                    ┌────────▼─────────┐
                    │   Read Replica   │ ← Analytics, Logs,
                    │   (Copy of DB)   │   Non-real-time reads
                    └──────────────────┘
Read Replica rule: Always write to Primary. For real-time reads, use Primary. For analytics/reports where slight delay is okay, use Read Replica — this reduces load on the Primary.

Caching with Redis

⚡ Cache Logic — Check Cache Before DB
  Request comes in for data
         |
         ▼
  ┌──────────────┐
  │  Redis Cache │ ◄── In-memory, super fast
  │ (Check here  │
  │   first)     │
  └──────────────┘
         |
    ┌────┴────────────────────┐
    │                         │
  Cache HIT               Cache MISS
  (data found)            (data not found)
    │                         │
    ▼                         ▼
  Return data          Query Database
  immediately          ↓
  (fast!)              Store result in cache
                       ↓
                       Return data
✅ Caching benefits: Fewer database queries → DB is under less load → faster responses → better user experience.

CDN — Content Delivery Network

Your servers might be in the US. A user in North India making a request has to travel all the way to the US and back — slow! CDN solves this.

CDN = Mini servers (Edge Servers) placed all around the world, caching your content close to users.

🌍 CDN Architecture (CloudFront)
             ┌─────────────────────────────────┐
             │        Your Main Server         │
             │      (Load Balancer + App)      │
             └────────────────┬────────────────┘
                              │ (origin)
          ┌───────────────────┼───────────────────┐
          ▼                   ▼                   ▼
  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐
  │  CDN Edge    │  │  CDN Edge    │  │  CDN Edge    │
  │  (US)        │  │  (N. India)  │  │  (Canada)    │
  └──────────────┘  └──────────────┘  └──────────────┘
         ▲                  ▲                 ▲
         │                  │                 │
   US users          India users         Canada users
   get served        get served          get served
   from nearby       from nearby         from nearby
   edge              edge                edge

How CDN Caching Works

First time someone in India loads a product photo → CDN edge in India doesn't have it → fetches from main server → caches it locally.
Next time any India user requests that photo → served directly from the India edge. No trip to the US server!

Anycast IP: How do all CDN edges share one IP? Through Anycast — multiple machines are assigned the same IP, and you're automatically routed to the nearest one.
CDN benefits:
✅ Much lower latency (serve from nearby)
✅ Less load on your main server
✅ Better user experience globally
AWS calls this: CloudFront

Full System — All Components Together

Here's how everything fits together in a real production system like Amazon:

1
User types amazon.com DNS resolves domain → returns CDN (CloudFront) IP via Anycast
2
CDN Edge checks cache If static content (images, CSS) is cached → serve it directly. No server needed!
3
Dynamic request → goes to API Gateway CDN forwards non-cached requests to the API Gateway (with rate limiting)
4
API Gateway routes to correct service /auth → Auth Service LB, /orders → Orders Service LB, /payments → Payment LB
5
Load Balancer distributes across server replicas Round-robin or other algorithms, health checks ensure only healthy servers receive traffic
6
Server checks Redis cache first Cache hit → return fast. Cache miss → query Primary DB, store in cache, return
7
Background jobs via Queue (SQS) Events (payment, order) published to SQS → Email Worker, WhatsApp Worker etc. process async
8
Fan-Out for multiple notifications SNS publishes one event → fans out to multiple SQS queues → WhatsApp + Email + SMS all triggered
9
Auto-scaling based on traffic When traffic spikes (sale), new servers spin up. When traffic drops, servers removed. Only pay for usage.
