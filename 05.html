What is Back of Envelope Calculation?

The name "Back of Envelope" comes from the idea of doing rough calculations on the back of an envelope — quick, approximate, not exact. In system design, it means estimating your resource needs before you build anything.

Definition: A quick, rough estimation to figure out how many servers, how much storage, and what database scale your system needs — based on expected user traffic. No exact numbers, just good approximations.
✉️
Why "Back of Envelope"?
Imagine you're at a meeting and someone says "how much storage will we need?" You grab the nearest envelope, flip it over, and do a quick rough calculation on the back. That's it — no spreadsheet, no calculator, just good approximations based on known numbers.

This concept was popularized by Jeff Dean, a legendary Google scientist, in a famous presentation where he used these calculations to choose the best system design for Google's infrastructure.

Why Every Engineer Needs This Skill

When your team wants to deploy a new system, the DevOps team will ask you these questions. If you can't answer them, you're guessing blindly — which wastes money or causes crashes.

❌ Without This Skill

  • DevOps asks: "How many servers?"
  • You guess: "Uh... give me 8 CPUs?"
  • You get 8 CPUs — but only need 2
  • You're wasting money on idle resources
  • OR you under-provision and it crashes
  • You look like a junior who doesn't know their system

✅ With This Skill

  • DevOps asks: "How many servers?"
  • You say: "My DAU is 150M, 3500 QPS average, so 2 servers with 4 CPU each, auto-scale at 70% CPU"
  • Confident, reasoned answer
  • Right-sized resources = cost savings
  • Critical for senior engineer / architect roles
  • Also asked in system design interviews!

DevOps teams always ask:

📋 Questions DevOps Will Ask You
How many servers?→ derived from QPS
Server configuration?→ CPU & RAM per server
How much disk storage?→ derived from data per user × users × time
Database configuration?→ CPU, RAM, IOPS for DB server
SSD or HDD? How many GB?→ derived from storage estimation

🚀 Fast (use these whenever possible)

  • RAM / Memory — nanoseconds. Redis, in-memory caches
  • CPU Cache — sub-nanosecond. Automatic
  • Local network — sub-millisecond

🐢 Slow (avoid if possible)

  • Disk seeks (HDD) — 10ms. Avoid random reads
  • Cross-region calls — 150ms+. Use CDN/edge caching
  • Network I/O — compress before sending
The #1 rule from latency numbers:
Memory is fast. Disk is slow.
That's why Redis (in-memory cache) is so much faster than a database query (disk I/O). Always try to serve reads from memory. Only go to disk for writes that must persist.
Practical takeaways:
• Avoid disk seeks wherever possible — design your data access to be sequential, not random
• Compress data before sending it over the network — simple algorithms are fast enough
• Use CDN to serve users from nearby servers — cross-region latency kills UX
• Data center round trips cost time — minimize cross-service calls

Worked Example — Estimating Twitter's QPS

Problem: "We're building a Twitter clone. Estimate the QPS (Queries Per Second) and storage requirements."

Step 1: Write Down Your Assumptions

📋 Assumptions (always write these first!)
Monthly Active Users300 million
Daily active %50% of MAU use it daily
Tweets per user per day2 tweets (average)
Tweets with media10% of tweets have a photo/video
Data retention5 years
Media size per tweet~1 MB average
⚠️ These are ALL approximate! 50% daily active could be 40% or 60%. 2 tweets/day could be 1 or 3. That's totally fine — this is estimation, not measurement.

Step 2: Calculate Daily Active Users (DAU)

📊 DAU Calculation
1
Monthly Active Users
MAU = 300 million
2
50% use it daily → Daily Active Users
DAU = 300M × 50% = 150 million
→ 150 million users active every day

Step 3: Calculate Average QPS (Tweet Writes)

🔢 QPS Calculation
1
Total tweets per day
150M users × 2 tweets/day = 300 million tweets/day
2
Divide by seconds in a day (≈ 100,000)
300,000,000 / 100,000 = 3,000
→ Average QPS ≈ 3,500 tweets per second
3
Peak QPS (assume 2× during a major event)
3,500 × 2 = 7,000
→ Peak QPS ≈ 7,000 tweets per second
✅ What this tells you:
• Your database must handle 3,500 INSERT operations per second on average
• Your system must handle up to 7,000 writes per second during peak (elections, breaking news, etc.)
• Design your auto-scaling policies and DB configuration around these numbers

Worked Example — Estimating Twitter's Storage

What does each tweet store?

📦 Per-Tweet Data Sizes
Tweet ID (UUID)64 Bytes
Tweet text (140 chars avg)140 Bytes
Media (photo/video, if present)~1 MB
Total per text tweet≈ 204 Bytes ≈ ~200 Bytes
Total per media tweet≈ 1 MB + 200 Bytes ≈ ~1 MB

Calculate Daily Media Storage

💾 Daily Storage Calculation
1
Total tweets per day
150M users × 2 tweets = 300M tweets/day
2
How many tweets have media? (10%)
300M × 10% = 30 million media tweets/day
3
Storage for media tweets (1 MB each)
30M × 1 MB = 30 million MB = 30 TB per day
→ ~30 Terabytes of media storage needed per day
4
5-year total storage
30 TB/day × 365 days × 5 years
= 30 × 365 × 5 ≈ 30 × 2000 = 60,000 TB
= 60 Petabytes (PB)
→ ≈ 55–60 Petabytes of storage needed over 5 years
✅ What this tells you:
• You need ~30 TB/day of object storage (like AWS S3) provisioned
• Over 5 years, plan for ~55-60 Petabytes of total storage
• You'll need a distributed file system / object storage (not a regular DB!)
• Budget for storage costs at this scale before starting

The Three Golden Rules

🔢

Rule 1: Round Everything

86,400 seconds → say "1 lakh." 99,987 / 9.1 → say "100,000 / 10 = 10,000." Never do exact math here.

📝

Rule 2: Write Assumptions

Always explicitly write down your assumptions first. DAU, posts per day, media %. They can always be challenged and updated.

🏷️

Rule 3: Label Your Units

Don't write "5." Write "5 MB" or "5 TB" or "5,000 requests/sec." Unitless numbers are meaningless in estimates.

The most common mistake: Forgetting to label units. "I calculated 30" — 30 what? Bytes? Terabytes? Millions? Always write the unit alongside the number.

What are Commonly Estimated?

📊 QPS (Queries Per Second)

  • Average QPS = normal load
  • Peak QPS = spike load (2× or more)
  • Tells you: DB write/read capacity needed
  • Tells you: Number of server replicas
  • Formula: (DAU × actions/day) ÷ 86,400

💾 Storage Requirements

  • Daily storage = DAU × data per user/day
  • Total storage = daily × 365 × years
  • Tells you: S3 bucket / disk provisioning
  • Tells you: Whether you need CDN, compression
  • Tells you: Long-term infrastructure cost

Real-World Workflow (How Engineers Actually Do It)

In practice, you don't always have production data upfront. Here's the actual workflow engineers follow when starting a new project:

🔄 Real Engineer's Workflow
1
Start with bare minimum resources
Deploy on a small machine first: 2 CPU, 4 GB RAM, 256 GB SSD
2
Run in dev environment with real team (~8–10 users)
Monitor CPU usage, memory, QPS, network in/out
3
Extrapolate to production scale
If 10 users use X CPU, then 1000 users = 100X CPU. Adjust machine size accordingly.
4
Deploy to production with estimated resources
Keep monitoring. Adjust as real traffic data comes in.
5
Iterate and improve estimates over time
Experience teaches you. Each deployment makes your next estimate more accurate.
Pro tip from the video: Start lean on purpose. Deploy with less resources than you think you need. This forces you to see how your code actually performs under real constraints, and you avoid wasting money on idle over-provisioned hardware.
🧪
Think of it like cooking: Before cooking for 1000 guests, you first cook for 10 and time how long each step takes. Then you extrapolate: if 10 takes 30 minutes, 1000 will take about 300 minutes (with some parallelism). That's back-of-envelope estimation for real kitchens!
