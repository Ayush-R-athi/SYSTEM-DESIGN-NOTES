What is CQRS? (The Big Idea)

CQRS stands for Command Query Responsibility Segregation. It's a system design pattern that separates the "write" and "read" parts of your application into completely independent systems.

CQRS in one line: Don't use the same code, same server, or same database for reading data and writing data. Split them completely.

CRUD has four operations: Create, Read, Update, Delete. CQRS splits these into two groups:

⚡ Command Side (C, U, D)

  • Create a product
  • Update a price
  • Delete an order
  • Any action that mutates data
  • Think: "Do something"
↔

🔍 Query Side (R)

  • Get product details
  • List all orders
  • Search by category
  • Any action that only reads data
  • Think: "Ask a question"
⚠️ Disclaimer from the video: CQRS is NOT for small apps. It adds a lot of complexity. Only use it when you genuinely have a scaling problem that simpler approaches can't solve. Large-scale companies like Amazon, Netflix, and Uber use it — not your hobby project.

Traditional Architecture & Its Bottleneck

In a standard app, every request — whether it's a GET, POST, PUT, or DELETE — hits the same server, same controller, and same database. This works fine at small scale, but creates a serious problem at Amazon-level traffic.

📦 Traditional Architecture (All in One)
  User
   │
   ▼
  REST API (Django / Express / FastAPI)
   │
   ├── GET /products   → Controller → READ  from PostgreSQL DB
   ├── POST /products  → Controller → INSERT into PostgreSQL DB
   ├── PATCH /products → Controller → UPDATE in  PostgreSQL DB
   └── DELETE /product → Controller → DELETE from PostgreSQL DB

  All operations → ONE database ← bottleneck!

The Locking Problem (at Amazon Scale)

Imagine earphones are listed on Amazon for $50. Thousands of users are reading the price simultaneously. Meanwhile, the seller wants to run a sale and update the price to $30.

🔒 Database Lock Conflict
  1000 users: "GET /products/earphones" → trying to READ price
                                           │
  Seller:     "PATCH /products/earphones" → trying to UPDATE price
                                           │
                                           ▼
                             UPDATE acquires a LOCK on the row
                                           │
                             All 1000 reads must WAIT until
                             the lock is released!
                                           │
                                           ▼
                           At Amazon scale (millions of users):
                           DB becomes a total BOTTLENECK 💥
❌ The core issue: Reads and writes are competing for the same database row at the same time. Updates acquire row-level locks. While a row is locked for writing, no one can read it. At massive scale, this creates extreme slowness or crashes.
3

CQRS: Splitting Commands & Queries

CQRS solves this by routing requests to completely different servers based on the HTTP method. The API Gateway is the traffic cop.

🚦 API Gateway Routing Rule in CQRS
           All users hit ONE API Gateway
                     │
           ┌─────────┴──────────┐
           │   Routing Rule:    │
           │  GET → Query Side  │
           │  POST  ┐           │
           │  PUT   ├→ Command  │
           │  PATCH │   Side    │
           │  DELETE┘           │
           └─────────┬──────────┘
                     │
       ┌─────────────┴─────────────┐
       ▼                           ▼
  ┌──────────────┐         ┌──────────────────┐
  │  COMMAND LB  │         │    QUERY LB      │
  │  (Writes)    │         │   (Reads only)   │
  └──────────────┘         └──────────────────┘
       │                           │
  Command Servers            Query Servers
  (validate, auth,           (just read &
   execute writes)            return data fast)

⚡ Command Side

  • Handles: POST, PUT, PATCH, DELETE
  • Validates the incoming data
  • Authorizes: "Are you allowed to do this?"
  • Generates a Command object
  • Writes to the Write Database
  • Emits an event after writing

🔍 Query Side

  • Handles: GET only
  • No write logic at all
  • No locking issues
  • Reads from Read Database
  • Data is pre-joined and ready
  • Optimized purely for fast reads
Key idea — Everything on the Command side is a "Command":
Instead of "controller runs SQL UPDATE", you generate a structured Command object like ProductUpdateCommand { id: 1, price: 30 } and pass it to the Write Model. This makes the intent explicit and traceable.
4

Two Separate Databases — Write DB & Read DB

This is the most important part of CQRS. You have two completely separate databases: one optimized for writing, one optimized for reading.

✍️ Write Database (Source of Truth)

Stores data in a normalized way — multiple tables with foreign keys, no duplication. Data integrity is the top priority.

Best DB type:

PostgreSQL MySQL ClickHouse (for logs)

Why SQL? Transactions, ACID guarantees, data integrity. You want the write side to be rock solid.

📖 Read Database (Optimized for Speed)

Stores data in a de-normalized way — all the data pre-joined into one big document. No JOINs needed at query time.

Best DB type:

MongoDB DynamoDB Elasticsearch

Why NoSQL? Fast single-document lookups, no JOINs, easy to scale horizontally.

How Are They Kept in Sync?

🔄 Sync Flow: Write DB → Event → Read DB
  Command comes in (e.g. price updated to $30)
           │
           ▼
  Write DB updated (PostgreSQL)
           │
           │ Emits an event: "PRODUCT_PRICE_UPDATED"
           ▼
     Message Queue (SNS/SQS or Kafka)
           │
           ▼
  Event Consumer (Lambda function)
           │
     Reads the event, rebuilds the product document
           ▼
  Read DB updated (DynamoDB / MongoDB)
  with pre-joined, de-normalized data
           │
           ▼
  Next read request → served instantly from Read DB ✅
✅ Result:
• Writes go to Write DB → no read locks on Read DB
• Reads go to Read DB → no write locks from Write DB
• Both databases can be scaled independently
• Read DB can use a completely different (faster) DB technology
5

Normalized vs De-normalized Data

This is the key to why the Read DB is so fast. Let's understand the difference.

📊 Normalized (Write DB — PostgreSQL)

  • Data split into many tables
  • No duplication
  • Use foreign keys to link tables
  • Need JOIN queries to combine data
  • JOINs are expensive at scale
  • Good for integrity; bad for read speed

📦 De-normalized (Read DB — MongoDB)

  • Data combined into one big document
  • Some duplication is OK
  • No foreign keys needed
  • No JOINs needed at query time
  • Single lookup by ID = full data
  • Perfect for fast reads

Example — Product Lookup

📋 Normalized (Write DB) — requires multiple JOINs
  products table:    { id: 1, slug: "earphones" }
  product_details:   { product_id: 1, price: 30, brand: "Sony" }
  product_stock:     { product_id: 1, available: 50 }
  product_orders:    { product_id: 1, total_sold: 200 }

  To get full product info:
  SELECT * FROM products
  JOIN product_details ON products.id = product_details.product_id
  JOIN product_stock   ON products.id = product_stock.product_id
  JOIN product_orders  ON products.id = product_orders.product_id
  WHERE products.id = 1
  → Multiple table scans, slow at scale 🐢
📦 De-normalized (Read DB) — single document lookup
  MongoDB document for product id:1 {
    "id": 1,
    "slug": "earphones",
    "price": 30,
    "brand": "Sony",
    "stock": 50,
    "total_sold": 200
  }

  To get full product info:
  db.products.findOne({ id: 1 })
  → ONE lookup, everything is already there 🚀
✅ Bonus safety net: If the Read DB ever gets corrupted or goes stale, you can always regenerate it entirely from the Write DB or event log. The Read DB is just a projection of the truth — the truth lives in the Write DB / event log.
6

Eventual Consistency — The Main Trade-off

There's a catch. Because Write DB and Read DB are separate and synced via an event/queue, there's a small delay between a write happening and the read side reflecting it.

⏱️ Timeline of a Write in CQRS
  T=0ms   Seller updates price from $50 → $30 (Write DB updated)
  T=10ms  Event emitted to message queue
  T=20ms  Lambda picks up the event
  T=50ms  Read DB updated to $30

  T=25ms  (another user reads price) → sees $50 ← old data!
  T=51ms  (another user reads price) → sees $30 ← updated ✅
⚠️ Eventual Consistency: The Read DB will eventually have the correct data — but there's a window (milliseconds to seconds) where it might show stale data. This is the trade-off you accept with CQRS.

✅ Eventual Consistency OK for:

  • E-commerce product prices
  • Social media posts/feeds
  • News articles, content sites
  • Analytics dashboards
  • Most read-heavy applications

❌ Eventual Consistency NOT OK for:

  • Stock market prices (real-time)
  • Bank balances (must be exact)
  • Medical records
  • Inventory (if overselling is catastrophic)
  • Any "must be consistent NOW" scenario
The honest trade-off:
Option A: Keep one DB, stay consistent — but DB crashes under load at Amazon scale.
Option B: Use CQRS, tolerate small delay — but stay scalable, fault-tolerant, and alive.

Most large-scale companies choose Option B.

CQRS + Event Sourcing Together (Natural Fit)

Remember Event Sourcing from Video 3? CQRS and Event Sourcing are like peanut butter and jelly — they naturally fit together.

How they combine: Instead of writing the final state to the Write DB, you write events (logs) to an append-only log (Kafka). The Read DB is then populated by replaying those events via Hydration.
🔗 CQRS + Event Sourcing Combined
  Without Event Sourcing:
  Command → Write DB stores final state
         → Event emitted → Read DB updated

  With Event Sourcing:
  Command → Kafka (Append-Only Log) stores every event
         → Consumer reads log → Hydration
         → Read DB built from replayed events

Write DB (Event Sourcing style)

  • Stores ALL events/commands as logs
  • Append-only — never updates, never deletes
  • Uses Kafka / ClickHouse / event store
  • Source of absolute truth
  • Full history forever

Read DB (Projection)

  • Built by replaying events
  • Stores de-normalized, query-ready data
  • Uses DynamoDB / MongoDB
  • Can be fully regenerated if corrupted
  • Just a projection — not the truth
✅ Superpower of combining CQRS + Event Sourcing:
If your Read DB ever gets corrupted or you want to switch DB technology (say MongoDB → DynamoDB), you just replay all events and regenerate the entire Read DB from scratch. Zero data loss. No migration scripts. The event log is the master record.
🏦
Think of it like a bank:
Write DB = the ledger of every transaction ever made (event log)
Read DB = the account balance displayed on your app (projection)

The balance on your screen is computed from the ledger. If the screen shows the wrong number, you don't fix the screen — you replay the ledger.

CDN Cache Invalidation (Bonus Optimization)

On top of CQRS, you can add a CDN like CloudFront to cache GET responses at the edge — so repeat reads don't even hit your Query servers.

🌐 CDN + Cache Invalidation Flow
  First GET for product id:1
       │
       ▼ CloudFront (cache MISS)
       │
       ▼ Query Server → DynamoDB → returns data
       │
       ▼ CloudFront caches the response

  Next 1000 GETs for product id:1
       │
       ▼ CloudFront serves from cache ← no server hit!

  Now seller updates the price:
       │
       ▼ Command path runs (Write DB + Read DB updated)
       │
       ▼ Lambda also triggers cache invalidation:
         "invalidate /products/1 from CloudFront"
       │
       ▼ Next GET → CloudFront cache is empty → fresh fetch
       ▼ New cached response stored with updated price ✅
✅ Why this is powerful: 99% of reads can be served from CloudFront edge servers near the user — zero database hits, zero server hits, near-zero latency. Only when data actually changes does the cache get cleared and refreshed.

When to Use CQRS & Full Summary

✅ Use CQRS When...

Good Fit

  • Read and write traffic scales very differently (e.g. 1000× more reads than writes)
  • You want different DB technologies for reads vs writes
  • You need to JOIN data from multiple microservices for reads
  • Eventual consistency is acceptable in your domain
  • You're building at Amazon / Netflix / Uber scale
  • You want a full audit trail (pair with Event Sourcing)

❌ Bad Fit

  • Small or medium-sized applications
  • You need real-time strong consistency (stock market, banking)
  • Your team is small and can't manage the complexity
  • Your read and write traffic are similar in volume
  • You're just starting out / building an MVP

Full Concept Summary

⚡

Command

Any action that changes data — create, update, delete. Represented as a structured Command object, not a direct SQL query.

🔍

Query

Any action that only reads data. Completely isolated from writes. Can use a totally different, read-optimized database.

✍️

Write DB (Normalized)

The source of truth. Data is split across multiple tables with foreign keys. SQL databases like PostgreSQL work well here.

📖

Read DB (De-normalized)

A projection of the Write DB, pre-joined for fast reads. No JOINs at query time. NoSQL like DynamoDB/MongoDB works well here.

⏳

Eventual Consistency

A small delay exists between writing and the read side reflecting it. Usually milliseconds. Acceptable for most (not all) apps.

🔗

CQRS + Event Sourcing

Instead of writing final state to Write DB, write events to an append-only log. Read DB is built by replaying those events.

📢

Fan-Out (SNS + SQS)

After a write, SNS publishes the event. Multiple SQS queues fan out to different consumers: one updates Read DB, one sends emails, etc.

🔄

Read DB Regeneration

If Read DB gets corrupted or you want to switch technologies, replay all events from the Write DB/event log to regenerate it completely.
